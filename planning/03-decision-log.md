## D-01 — Node 26 LTS, TypeScript 6.0 (not 7)

- **Question.** Which runtime and compiler versions?
- **Options.** Node 22 / 24 / 26; TypeScript 6.0.x / 7.0.x.
- **Decision.** Node 26 LTS, pinned in `.nvmrc`, `engines` and the Docker image. TypeScript pinned to `~6.0.3`.
- **Why.** Use the newest LTS for a new service: longest support window, and it is what the developer machine already runs. TypeScript 7 is npm's `latest`, but `@nestjs/swagger` 12 and `ts-jest` 29.4 both declare they do not support it, and NestJS's own starter pins `^6.0.2`. Following `latest` blindly would break the build. Node 26 also brings `Temporal`, and TypeScript 6.0 ships its typings — D-09 relies on both.
- **Basis.** [V] V-1, V-2, V-8. [BP] "Run production on an LTS line" (Node.js release policy).
- **Confidence.** High.
- **Would change my mind.** `@nestjs/swagger` and the test transformer both adding TS 7 to their peer ranges.
- **Round 1.** **Accepted.** Not contested.
- **Round 2.** Not contested.

## D-03 — PostgreSQL 18 over MongoDB

- **Question.** MongoDB or PostgreSQL? (The brief demands a justification.)
- **Options.**
  1. **PostgreSQL**, relational tables.
  2. **MongoDB**, one document per entry with embedded sets and precomputed per-entry summaries (this was the previous, now deprecated, plan).
- **Decision.** PostgreSQL 18.
- **Why.**
  - The hard parts of the brief are relational-shaped: PR aggregation over sets, period comparison and atomic multi-entry writes.
  - **Exact decimals**: `numeric` is exact; unit conversion and PR ties should not depend on binary floats. MongoDB's `Decimal128` works but is awkward through drivers/ODMs.
  - **Transactions by default**: an atomic bulk insert is one transaction over two tables, and PostgreSQL does that with no setup. MongoDB can do it too — on a replica set, and a single-node one is a small compose change — so this is a convenience, not an argument that decides the choice.
  - **Constraints in the database**: `CHECK (reps >= 1)`, `NOT NULL`, composite keys — "validation at boundaries" includes the last boundary.
  - **Keyset pagination** has first-class row-value comparison; in MongoDB the three-column cursor needs a hand-built `$or` ladder.
  - **Observability of the design**: `EXPLAIN (ANALYZE, BUFFERS)` output in the README is direct evidence for "indexing strategy" and "query efficiency".
- **Honest case for MongoDB.** The request body *is* the document; one write per entry; `userId` is a natural shard key. The stack-fit argument turned out weaker than assumed: Everfit's posting lists MongoDB **and** PostgreSQL (U-1, checked).
- **Basis.** [V] V-3, V-4, U-1 (checked). [K] K-9. [J] problem-fit beats stack-fit when the brief offers both options explicitly.
- **Confidence.** High (was Medium; the open risk was stack-fit, and it has been checked).
- **Would change my mind.** A requirement for schemaless per-exercise set attributes (tempo, RPE, distance…) that vary by exercise type.
- **Round 1.** **Accepted.** Keep from all four strong reviewers. The README carries a short "the same design in MongoDB" section — what the document, the indexes and the PR pipeline would look like — so the choice reads as a decision between two understood options.
- **Round 2.** **Accepted** — kept by all three reviewers. One correction (A-10): the claim that a replica set "complicates `docker compose up`" is dropped. One reviewer pointed out that a single-node replica set is a small compose change (recalled by the reviewer, not checked here) and that an interviewer who runs MongoDB knows it. The README's MongoDB section now shows the entry document, the index `{ userId: 1, date: -1, _id: -1 }` and the `$unwind` / `$sort` PR pipeline rather than describing them.

## D-04 — Drizzle ORM for queries; hand-written SQL migrations

- **Question.** How does the code talk to PostgreSQL, and what defines the schema?
- **Options.** Prisma 7; TypeORM 1.x; Drizzle 0.45; Kysely; raw `pg`.
- **Decision.** Drizzle ORM (pinned 0.45.x) over `pg` for queries; all queries live in repository classes. **Migrations are SQL files written by hand and are the only source of truth for the schema.** `schema.ts` exists for query typing and is never fed to `drizzle-kit generate` or `push`.
- **Why.** The graded queries (keyset row comparison, a CTE with three top-1 picks, a covering index) are SQL-first. Drizzle keeps them as typed SQL instead of hiding them behind an ORM query language. Its schema DSL cannot express everything this schema needs — `INCLUDE` columns are an open feature request (U-2, checked) — so generating migrations from it would produce a schema different from the one designed. One rule is simpler to defend than two: the SQL a reviewer reads is the SQL that runs. `drizzle-kit generate --custom` creates the empty migration file and the standard migrator applies it (V-11). `schema.ts` cannot silently drift far, because the integration tests run the real migrations and the real queries against PostgreSQL.
- **Risk accepted.** Drizzle is pre-1.0 (1.0 is at rc.5). Mitigation: exact version pin; nothing outside `database/` and the repositories imports it.
- **Basis.** [V] V-1 (versions, Prisma tag), V-11, U-2 (checked). [J] fit to SQL-heavy grading.
- **Confidence.** Medium.
- **Would change my mind.** Drizzle getting in the way of the keyset or PR queries during the first slices → Kysely + the same SQL migrations (same philosophy), not Prisma.
- **Round 1.** **Revised.** The first text said "`drizzle-kit`-generated SQL migrations" in the decision and "hand-reviewed SQL is the source of truth" in the rule under it; Grok pointed out the two disagree. Now one statement. Opus's CI drift check (`drizzle-kit pull` compared with `schema.ts`) is optional and the first thing dropped. Gemini's "replace Drizzle with Kysely now" was not followed: its claim about what Drizzle cannot express was recall, and the design no longer depends on the DSL.
- **Round 2.** Kept by all three reviewers; no change. One reviewer's point is the reason the drift check can be cut: the integration tests on a real database are what catches typing drift. The check was optional and second on the cut list (D-26).
- **Round 3.** The drift check is cut from the start (3C-1 (a), D-26).

## D-06 — Two tables (entries + sets), append-only, no derived columns

- **Question.** What is the shape of stored workout data?
- **Options.**
  1. **Fully normalised**: `workout_entries` + `workout_sets`; PRs join the two.
  2. **Entry row with `sets jsonb`** plus summary columns (the Mongo design ported to PostgreSQL).
  3. **Normalised sets + three per-entry maxima** (`max_weight_kg`, `max_volume_kg`, `max_e1rm_kg`) written once at insert.
  4. Sets table with `user_id`/`exercise_key`/date copied onto every set row and PR indexes on sets.
- **Decision.** Option 1. Entries are immutable in v1. Option 3 is the second rung of the measured fallback ladder (D-11).
- **Why.** Sets as rows give per-set constraints and ad-hoc SQL, and room for per-set attributes later. The first proposal chose option 3 for two reasons, and both fell:
  - *"Without the columns the formulas must be written twice, in TypeScript and in SQL, and kept in agreement including rounding."* Ranking does not need the rounded formulas. It needs three exact products — `weight_kg`, `weight_kg × reps`, `weight_kg × (30 + reps)` — with no division and no rounding. That is trivial in both places, and one test asserts they agree.
  - *"The join reads about 200 000 set rows."* Only for a user who logged one exercise 50 000 times. A committed lifter's most-trained exercise has 2 500–4 000 entries of six to ten sets, warm-ups included: 15 000–40 000 set rows.
  With those gone, the smaller schema wins: three fewer columns, no stored-versus-computed invariant to test, and changing a formula never needs a backfill. One cost stays real and is what the benchmark measures: `workout_sets` has no `user_id`, so the sets of a user's exercise can be reached only through its entries. How the planner runs that join — a nested loop with one primary-key lookup per entry, or a hash or merge join — is its choice; the benchmark records the plan that ran.
- **Basis.** [K] K-6. [BP] denormalise only when a measurement asks for it. [J] performance awareness is graded (V1, V7) — and is shown by measuring, not by pre-building.
- **Confidence.** Medium — it now rests on a measurement that has not been run (U-8).
- **Would change my mind.** The benchmark: if the join misses its budget for the realistic heavy user, the ladder of D-11 applies in order — first a covering primary key on the sets and extended statistics, which change nothing that is stored; then the three maxima as the `INCLUDE` payload of `ix_entries_exercise`. The maxima stay safe to store because entries are immutable.
- **Round 1.** **Revised** — the most contested item, a 2–2 split: Grok and Astra for the join first, Gemini and Opus for keeping the columns. The author first rejected Grok's version, then reversed after Astra removed the main objection (exact ranking) and proposed running both shapes on the same data. The candidate chose the join first. `time_known` is a new column from D-09.
- **Round 2.** **Revised**, in detail only; the shape was kept by all three reviewers. A-2: the `set_count` column the revision had added to design §5 is dropped — nothing read it. A-6: "one pass" and "one probe per entry" described one possible plan, not a property of the schema, and are reworded here and in D-11. B-13: one reviewer wanted `INCLUDE (reps, weight_kg)` on the sets primary key from the start; it is measured first and became the first rung of the fallback ladder. B-12: the benchmark's main lifts carry six to ten sets, warm-ups included.
- **Round 4.** `workout_entries` gains `utc_offset_minutes`, the offset the client sent, for display only (D-09). It is stored as sent, not derived, so the rule of no derived columns stands.

## D-07 — Free-text exercise name → normalised key; catalog in the database, seeded from a JSON file

- **Question.** What identifies an exercise, and where does the muscle-group mapping live (X2)?
- **Options.** (a) mapping hardcoded in code — forbidden; (b) JSON file read into memory at boot; (c) database tables as the source of truth, edited through an admin API, with the JSON file as the initial seed; (d) file as the reviewed source of truth, synced into database tables at every deploy.
- **Decision.** (c). Entries store `exercise_name` (as typed) and `exercise_key` (NFKC, trim, collapse whitespace, lowercase). The catalog is four small tables (`muscle_groups`, `exercises`, `exercise_muscle_groups`, `catalog_seed_ledger` — design §5). One function, `exerciseKey(name)`, makes the key for logging, for every catalog write, for the catalog routes and for the seed. `seed/exercise-catalog.seed.json` is the catalog's initial content: the one-shot `migrate` step gives each of its items to a database once (D-27). Each API process reads the catalog through an in-memory snapshot, reloaded every five minutes and at once on the replica that handled a write. Entries have no reference to the catalog; unknown exercises are accepted and simply have no muscle groups. No aliases in v1. Business logic depends on the `ExerciseCatalog` interface, which did not change. Who may write, and what a rename or a delete does, is D-27.
- **Why.** The owner's requirement: exercises are updated often, and a change must not need a developer or a deploy. That is this entry's own earlier "would change my mind" ("a need to edit the mapping without a deploy → a table-backed adapter behind the same interface"), and it has fired. (b) fails it by construction. (d) fails it too: while the file is the source of truth, every change is still a commit and a deploy. Only (c) makes the database the place where the catalog is edited.
- **What still holds from the file design.**
  - The brief's wording ("if exercise metadata is available") implies exercises without metadata exist, so unknown exercises stay loggable.
  - Normalising to a key makes "Bench Press", "bench  press" and "BENCH PRESS" one exercise for PRs.
  - The mapping is data, not business logic, as X2 asks — more plainly now than when it was a file.
  - Entries hold no reference to the catalog and groups are resolved at read time, so a catalog correction corrects history.
  - The muscle-group filter is still a list of keys taken from memory (`exercise_key = ANY($keys)`): no join, no subquery for the planner to mis-order. The history query and its benchmark are unchanged.
  - Aliases stay out: merging names silently changes PRs and needs product rules.
- **What the requirement overturns.** Round 1 chose the file with these arguments, and each rested on a premise that is now false:
  - *"To serve an admin workflow nobody has asked for."* It has been asked for. Neither the author nor any reviewer asked the owner how often exercises change; four round-1 reviewers and all three round-2 reviewers ruled for the file on that unchecked premise.
  - *"Two tables, an index, a script and a compose step."* The tables and a seed script are back (four tables, no secondary index); the seed runs inside the existing `migrate` step, so there is still no extra compose service.
  - *"A second copy that can drift from the file the reviewer is reading."* The roles are reversed: the database is the source of truth, the file is a seed, and the seed never overwrites a row.
  - *"An invalid file stops the service from starting."* It now stops the `migrate` step, so `api` never starts on a bad seed file.
  - *"Saves 0.5–1.5 h."* The catalog now costs about 2.75 h (D-26).
- **Basis.** The owner's requirement. [J] on every mechanism. [K] In the real product exercises are entities (coaches create custom ones). [V] V-20 (what a load costs; why a counter must be a row bumped inside the write).
- **Confidence.** Medium — High on the direction, which is the owner's call; Medium on the mechanisms, which round 3 kept with changes.
- **Would change my mind.** Tags that must converge across replicas within seconds (→ the version row of design §10.8; `LISTEN`/`NOTIFY` only if seconds are not enough); a catalog of many thousands of rows (→ a paged listing, and reads per request instead of a full snapshot); exercises that belong to one user or one coach (→ a scoped catalog, which is a different model).
- **Round 1.** **Revised**, from (d) to (b). Change from all four strong reviewers; the first decision log had named it as the fallback. Saves 0.5–1.5 h.
- **Round 2.** (b) kept by all three reviewers. One addition (B-5): a check that the built image starts from a clean checkout — at that time for the catalog file, now for the seed file and the migrations, which must still reach the image.
- **After round 2 — the owner's requirement.** **Revised**, from (b) to (c), and reviewed in round 3 (below). The owner fixed the direction; the author settled the mechanisms:
  - *Reads.* Options: read the tables on every request; `LISTEN`/`NOTIFY`; a version row polled, with a reload on change; a whole snapshot in memory reloaded on a timer. Choice: the snapshot, every 30 s (`CATALOG_REFRESH_SECONDS`; 300 s since the catalog refresh review, below), plus an immediate reload on the replica that handled the write. Why: it keeps the history query shape the benchmark measures and adds no read per request, for data that changes a few times a day at most; a push needs a dedicated connection per replica and still needs the timer for a replica that was disconnected.
  - *The key.* Options: a database `CHECK` or generated column repeating the rule; one TypeScript function. Choice: one function, no `CHECK`. Why: PostgreSQL's `lower()` and whitespace classes differ from JavaScript's at the edges, and two implementations of one rule is how two keys stop matching. An integration test holds it (log `"  ZERCHER   squat "`, create `"Zercher Squat"`, the entry shows the groups).
  - *Failure.* At boot the process waits about ten seconds for the first load, then exits non-zero. At refresh it keeps the last good snapshot, logs a warning with its age and retries at the next tick; readiness does not fail for a stale catalog. Why: thirty-second-old muscle-group tags are a smaller problem than a replica taken out of rotation, and a process that never loaded a catalog would tag every entry with no muscle groups and call it an answer.
- **Round 3.** **Kept, with modification**, by all three reviewers; the direction was not contested. 3B-3: a request takes one snapshot and uses it throughout, so a response is never a mixture of two catalog versions; a refresh is single-flight and numbered, so an older load can never replace a newer one; the load is one statement; the refresh after an admin write runs after the commit and never fails the write. 3A-9: the first load runs in `onModuleInit`, so the process does not listen until it succeeds, and `api` has `restart: on-failure`. 3B-4: the muscle-group filter checks the group and takes its key list from the same request snapshot; the README says another replica can show the old catalog for up to 30 seconds. 3B-5: a golden test pins `exerciseKey()`, and one `muscleGroupName()` is used by the admin API, the seed file and the filter; changing either function is a data migration. 3A-11: the `migrate` step is one compiled entry point, `src/cli/migrate.ts`. Not followed: starting without a catalog (it would answer with empty muscle groups as if that were the data), and serving the catalog GETs from the snapshot (an admin checking a change should see the database).
- **After round 4 — the catalog refresh.** **Revised**, in detail. The owner questioned the 30-second interval, which nothing derived. Measured on PostgreSQL 18.7, a full load costs 2.6 ms and 26 KB (V-20), so cost was never the reason to change it; the interval bounds how long tags on other replicas lag, minutes are acceptable for tags, and it is now 300 seconds (the owner). A failed refresh is tried once more after 10 seconds (the author). The owner kept the polled version row and a reload on an unknown filter group out of v1 and put both in the plan for scale (design §10.8), because with one `api` neither reacts to anything but SQL typed by hand. Not reviewed by another round.

## D-08 — Unit registry in code with aliases, decimal arithmetic, exact kilograms, no DB enum

- **Question.** How are units modelled so that adding one is minimal (X1), and how is conversion kept exact (F1.2)?
- **Options.** Strategy class per unit; a `switch`; a data-driven registry (code); a `units` table in the database; env/JSON config.
- **Decision.** One array of `{ code, label, kgPerUnit, aliases }` in `weight-units.ts`, wrapped by an injectable `UnitRegistry`. Lookup trims and lower-cases, then matches the code or an alias (`lbs` → `lb`, `kgs` → `kg`); the canonical code is what is stored and returned. Factors are decimal strings; math uses `decimal.js`; `weight_kg` is the exact product, stored in `numeric(17,11)` and never rounded on write; originals are `numeric(9,3)`. The `unit` column is plain text with no enum or CHECK.
- **Why.** All weight units are linear, so a factor table is the whole abstraction — a class per unit would be ceremony. Everything that mentions units (validator, error text, the OpenAPI description and output enum, `/units`) derives from the registry, so adding stone is one line and zero migrations. A conversion factor is a physical constant, not deployment configuration, so it belongs in reviewed code rather than env or a table. A DB enum/CHECK would turn a new unit into a migration, defeating X1; integrity is preserved because `weight_kg` is always stored.
  - *Aliases.* "lbs" is how people write pounds, and `KG` is what a hurried curl sends. Rejecting them fails a reviewer's first request for no gain. Aliases live in the same one list, so a new unit is still one line.
  - *Exact kilograms.* An input has at most three decimals and a registered factor at most eight, so the product has at most eleven and `numeric(17,11)` stores it whole (`225 lb` → `102.05828325 kg`); a registry test fails on a factor with more than eight decimals or a unit whose largest accepted weight would not fit. Four decimals — the round-1 outcome — are fine for ordering *different* loads and break *equal* ones: `100 lb × 10` and `200 lb × 5` are the same volume, 453.59237 kg, and four-decimal storage made them 453.5920 and 453.5925, so the later workout took the record. `200 lb × 5` and `175 lb × 10` tie on estimated 1RM and split the same way. The tie rule (D-11) cannot work on numbers that are no longer equal.
- **Basis.** [K] K-1, K-8, K-14. [V] V-4 (numeric exact). [BP] never use binary floating point where equality of decimal quantities matters.
- **Confidence.** High.
- **Would change my mind.** A non-linear unit (none exists for weight). `decimal.js` vs float-with-rounding is arguable; floats would also pass every realistic test.
- **Round 1.** **Revised** (aliases and case-insensitive matching added — found by the author in the realism audit, not by a reviewer). Opus and Astra independently argued for storing kg unrounded (eleven decimals); the author accepted it on the arithmetic and the candidate rejected it on the premise — the example weight, `88.185 lb`, is just 40 kg written in pounds. **Four decimals confirmed; the proposal is withdrawn** (summary 11.1).
- **Round 2.** **Revised** — the round's one substantive split, and a reversal of the round-1 outcome (C-1, the candidate's call). Two reviewers kept four decimals; the third showed a tie that ordinary pound plates produce (`100 lb × 10` against `200 lb × 5`), which is the real case the round-1 realism test had asked for and not been given. Exact storage removes a rounding step rather than adding machinery. Tests: the registry width test, and two fixed cases in which the earlier entry keeps the record. Also B-10: in OpenAPI `unit` is a string with the accepted spellings on input and an enum on output. The alias list (the author's call in round 1) was reviewed and kept; full-word aliases were not followed — no client named that sends them, and the 400 lists the spellings.
- **Round 3.** Kept. 3B-10: `decimal.js` precision is set to 40 and the registry test asserts it — the largest product has 18 significant digits, under the library's default of 20 (recalled), but the default is one global setting a later import could change. A weight is built as `new Decimal(String(n))`, and the three-decimal check runs on that text: an accepted weight such as `102.5` or `0.125` parses exactly from JSON, so nothing is lost before the check.

## D-09 — The UTC instant is the only time key; the client's offset is kept for display

- **Question.** What does `date` mean, how is it stored, and how do date filters work (E4)?
- **Options.**
  1. **Instant only** (`timestamptz`, UTC). Date filters are instants; reads take a `tz` parameter to turn dates/months into instant ranges.
  2. **Calendar date only** (`date`). No time, no timezone problem.
  3. **Both**: `performed_at timestamptz` + `performed_on date` — the decision of rounds 1–3.
  4. **Instant only, and reads take instants**: the caller turns its viewer's days and months into instants; the server takes no zone at all.
- **Decision.** Option 4, since the owner's change after round 3 (design §8):
  - Stored: `performed_at timestamptz(3)`, the only value any filter, sort, index or cursor uses; and `utc_offset_minutes smallint NULL`, the offset the client wrote, for display only (`420` for `+07:00`, `NULL` for `Z` or `-00:00`, −12:00…+14:00 in whole minutes). No local date, no flag, no zone name.
  - `date` has one format: an RFC 3339 date-time with `Z` or an offset (some ISO 8601 variants tolerated). The instant is kept, cut to the millisecond; the offset is stored beside it. A date alone and a date-time with no offset are 400s, each with its own message showing the fix and saying that `Z` means UTC, not local time. A zone in brackets is accepted and ignored. A client that knows only the day chooses the time; the README recommends noon in the athlete's own offset for a past day, and the current time for today if noon has not come.
  - One parser, `Temporal.Instant.from`; it also rejects a date that does not exist (`2025-02-30T09:00:00Z`).
  - Write bounds: no later than now + 15 minutes, not before `1900-01-01T00:00:00Z` (D-18).
  - Reads: `from` / `to` and the four compare bounds are instants forming `[from, to)` — `from` included, `to` excluded, said wherever a caller meets it — each usable alone, with the 1900 floor, rounded up to the millisecond, `from >= to` a 400 after rounding. A date alone is a 400 that says to send the start of the next day. A space where a query string turned `+` into one is read as `+`, for every accepted offset form, before validation. No zone parameter: the caller chooses the zone its periods are cut in.
  - Sort, cursor and indexes on `(performed_at, id)` (D-10); PR ties to the earliest instant (D-11).
  - Responses carry `date`, the stored instant printed with `toISOString()`, and `utcOffset` (`"+07:00"` or `null`); `performedAt` is gone.
  - No query uses the database session's zone; values are cut to the millisecond before they are written; tests run with a non-UTC process zone (`Asia/Ho_Chi_Minh`) against a test database whose session zone is another (`America/Los_Angeles`).
- **Why.**
  - **The traveller case.** Workouts at `2025-02-10T05:30:00+07:00` and `2025-02-10T20:30:00-07:00` are 29 hours apart; option 3 filed both under Feb 10, so no date range could separate them and no viewer's timeline matched the stored days. One instant gives every viewer one consistent timeline in their own zone (V-17).
  - The brief's `date` is a field name and mandates no type (the owner's reading); it recommends UTC storage, and this is UTC storage.
  - **`timestamptz`, not `timestamp`.** Neither stores a zone. `timestamptz` stores an exact moment and converts an offset in its input to UTC; `timestamp` stores a wall-clock reading, silently drops an offset in its input (V-19), and comes back through `node-postgres` as a `Date` read in the process's local zone (V-9), so one row would mean different moments on different machines. Both take 8 bytes. `datetime` is not a PostgreSQL type; a `bigint` of epoch milliseconds or a `text` ISO string saves nothing and loses readability, date functions or safe ordering. The front end gets an ISO string from `toISOString()` either way.
  - Nothing on the write path depends on the caller's zone: an offline phone that syncs later cannot file a workout under the wrong day, and no rule for daylight-saving gaps and overlaps is needed.
  - **One format, and a missing time is the client's to choose.** Back-filled sessions, a coach's spreadsheet and imported histories sometimes know only the day. The client knows the athlete's zone and the server does not: noon in the athlete's offset is the stated day for the athlete and for every viewer within twelve hours of them, while any time the server picked (noon UTC was considered) is a guess without that knowledge. One format also means every stored value is a real instant the client sent, so the server never presents an invented time and needs no flag to say so. The likely first request (`"date": "2025-02-10"`) is a 400 whose message shows the fix, and every example uses a full date-time.
  - No zone parameter on reads: the front end knows its viewer's zone; a second place to state it is a second place to get it wrong.
  - **The offset is kept, for display** (the owner's decision after round 4; all three reviewers asked for it). It is already in every request; once discarded it can never be recovered. It records where the athlete was at that moment, so unlike a user's settings zone it cannot go stale. It lets a client show "Feb 10, 05:30 (UTC+7)" for a morning workout whose `date` is the previous UTC day, and lets a later version build an athlete-day view from history already logged. It changes no filter, sort, index or cursor.
  - No user-settings table: a stored user zone would go stale exactly when the user travels.
- **Costs.** Periods are cut in a zone the caller chooses, and with no athlete profile a coach in another zone sees a workout on the day it fell in the coach's zone (a 06:00 Monday session in Hanoi is Sunday 15:00 in Los Angeles in winter, 16:00 in summer); `utcOffset` still shows the athlete's own clock, but filtering by the athlete's day is a later version. The offset is `NULL` for every client that sends `Z`, `toISOString()` included; such a workout is shown in the viewer's zone, and the README shows a client the one line that sends its local offset instead. A date alone is refused, so a reviewer's first request may need a second try, and a client that knows only the day must choose a time — midnight UTC, the easy choice, puts the entry on the previous day for viewers in the Americas. Every caller computes its own period bounds, daylight saving included (the README gives the recipe). A time a client invents cannot be told from a real one.
- **Basis.** [V] V-17 (the traveller pair, midnight and noon UTC across offsets, `+` in a query, the week across a daylight-saving change), V-18 (the round-4 checks), V-13 (`Temporal` parsing), V-9 (`node-postgres` and zone-less values), V-19 (PostgreSQL 18: `timestamp` drops an offset, `timestamptz(3)` rounds to the millisecond). [K] K-15 (what clients send), K-18 (`Z` under RFC 9557). [J] the owner's traveller case and the real-use review that followed it.
- **Confidence.** Medium (High that one instant gives a consistent timeline and on `timestamptz`; Medium on refusing a date alone).
- **Would change my mind.** A coach view by the athlete's own day → an athlete-day column derived from `performed_at` and `utc_offset_minutes`, filled for history already logged. Accounts with a profile → a user zone as a default for clients, never as stored data.
- *The three round lines below record the previous contract (option 3); the last two record the change and its review.*
- **Round 1.** **Revised.** Every strong reviewer agreed the `Z` rule was a real weakness; no two agreed on the fix — Grok: `date` accepts only a calendar date, plus a separate `performedAt`; Gemini: accept date-times with no offset; Opus: an optional IANA `timeZone`; Astra: keep the rules, return `performedAt: null`, no timezone database. The author's own first fix (an optional `localDate`) was dropped in favour of Opus's. The candidate chose `timeZone` and the helpful 400. Astra's concern about a timezone database is met by `Temporal`, which is part of Node 26 — no dependency is added. Storing the ordering key non-null with a `time_known` flag is the author's call while applying the list (a null would break keyset comparison); Opus and Astra had each proposed that shape.
- **Round 2.** **Revised**, in detail only; the contract stands. A-4: the offset-less 400 says the *instant* is unknown — the day is in the text — and still names the three fixes. A-8: the gap and overlap rule, written down. B-3: the parser is chosen by input shape, with tests for an offset sent with a zone and for fractional seconds. B-4: the ordering value moved from midnight UTC to 14 hours earlier, so a date-only entry no longer lands between the timed entries of its day for a user east of Greenwich. B-9: the test database runs in a non-UTC session zone. The two author's calls of round 1 here (`time_known`, `Temporal`) were reviewed and kept. Not followed: refusing wall times in a gap or overlap (it refuses a real workout), and `apk add tzdata` (not what `Temporal` reads; already covered by U-7).
- **Round 3.** Kept. 3A-5: a `Z` instant is converted with the zone `UTC` (`toZonedDateTimeISO('Z')` throws), and a calendar date is parsed with `Temporal.PlainDate.from`, so a date that does not exist (`2025-02-30`) is a 400 naming the field rather than a quiet roll-over. 3A-13: the ordering tests state that the date-only and the timed entry share a date.
- **After round 3 — the owner's time model.** **Revised** — option 3 replaced by option 4. The owner found the traveller case above, which no reviewer of rounds 1–3 raised, and decided the points listed in design §17 ("After round 3"): the instant only, one input format, half-open instant ranges with no zone, order on `(performed_at, id)`, and no settings table. A review of that direction against real use then added the write bounds, `date` as the response field and the `+` rule; the owner chose not to store the original offset (reversed after round 4, below). The same review proposed accepting a date alone as 12:00 UTC with `time_known` kept; that was applied, then reversed by the owner in favour of one format, because the client — not the server — knows the zone a missing time should be chosen in. Gone: `performed_on`, the `timeZone` field, the daylight-saving rule for wall times, the made-up ordering value and the `Z` caveat. Not reviewed by any model.
- **Round 4.** **Revised.** Three reviewers kept the instant as the only key, the half-open ranges and the order; all three asked for the client's offset to be kept, and the owner agreed (`utc_offset_minutes`, `utcOffset`). The owner also chose to accept a zone in brackets and ignore it. Applied with them: the advice for a missing time no longer collides with the future bound; `to` is said to be excluded wherever a caller meets it; the `+` repair covers every accepted offset form; two error messages; read bounds with the floor and rounded up to the millisecond. The author added the `timestamptz`-versus-`timestamp` reasoning and the offset range check. Afterwards the database facts it rests on were checked on PostgreSQL 18.7 (V-19), and the README plan gained the line a client needs to send its local offset instead of `Z`.

## D-10 — Keyset (cursor) pagination

- **Question.** Cursor or offset (F2.5)?
- **Decision.** Keyset on `(performed_at DESC, id DESC)` with an opaque base64url cursor `{ v, at, id }`; `limit` 1–100 (default 20); fetch `limit + 1` to compute `hasMore`; no total count. The cursor is built from the last row of the page **as stored** — `performed_at` to the millisecond, never the formatted response; with a cursor, the row-value condition on the index's leading columns starts the scan at the cursor.
- **Why.** At 50k+ rows, offset pages get linearly slower and shift when new entries arrive mid-scroll; keyset is constant-cost and stable. The cursor is opaque so the sort key can change without breaking clients (hence the version field). A total count would cost a full filtered scan per request for a number infinite-scroll UIs do not need.
- **Basis.** [BP] K-3. [K] row-value comparison is index-assisted in PostgreSQL.
- **Confidence.** High.
- **Would change my mind.** A UI need for "jump to page N" (then offer offset as an alternative mode, documented as slower).
- **Round 1.** **Accepted.** Two details added: the date-bound clamp (answering a planner question Gemini raised; confirmed by `EXPLAIN` in the benchmark), and README lines for back-dated entries and cursor reuse across filters. Binding the cursor to its filters (Grok) was not built: reuse under other filters gives an odd page, not wrong data.
- **Round 2.** **Accepted**; kept by all three reviewers. B-2: the cursor rule above is now written down and held by an integration test that is never cut — timed and date-only entries on the same days, walked at page size one, every entry exactly once in the documented order. A-5: the README says which back-dated entry a paging client misses — only one that sorts into the part of the list already read; one that lands below the cursor still appears on a later page. Binding the cursor to a filter hash was proposed again by one reviewer and not followed again: no real sender, and two reviewers leave it out.
- **After round 3 — the owner's time model.** **Revised**, in its key. The sort is `(performed_at, id)` because there is no local date any more (D-09); the date-bound clamp of round 1 is no longer needed, since the cursor's condition is on the leading index column. The never-cut walk now mixes entries on different instants with entries sharing one instant.

## D-11 — PRs computed on read, by joining entries to sets

- **Question.** Compute PRs when asked, or maintain them on write? And from what?
- **Options.** (1) aggregate on read; (2) `personal_records` table updated on every insert; (3) materialised view / periodic job.
- **Decision.** (1). The join of the user's entries of the exercise to their sets (date predicates only when sent) is evaluated once and materialised; three top-1 picks read that result, ranked by exact scores — `weight_kg`, `weight_kg × reps`, `weight_kg × (30 + reps)` — then the ≤ 3 winning entries are loaded by primary key. Ties → earliest instant, then lowest id, lowest set number. Values are divided, converted and rounded only for display. The `exercise` parameter is the whole name after normalisation; a name that matches nothing is a 200 with a fixed message (design §9.3).
- **Fallbacks, in order, only if the benchmark misses its budget.** (1) a covering primary key on the sets — `PRIMARY KEY (entry_id, set_number) INCLUDE (reps, weight_kg)` — so the join reads sets from the index alone, plus extended statistics on `(user_id, exercise_key)` so the planner's row estimate for one user's exercise is right; nothing that is stored changes. (2) the per-entry maxima of D-06 option 3 as the `INCLUDE` payload of `ix_entries_exercise`. (3) per-metric indexes, with each top-1 branch reading the table directly — a materialised CTE has no indexes, so the branches cannot go through it.
- **Why.** The brief asks for PRs over **arbitrary time ranges**; a maintained all-time table cannot answer "PR in October" without scanning anyway. Maintaining PRs on write introduces a read-modify-write race (exactly the concurrency case E5 warns about) and must be unwound if entries ever become editable. On-read is always correct by construction. Ranking by exact products means SQL and TypeScript cannot disagree, and the comparison never depends on a rounded intermediate.
- **Basis.** [K] K-6, K-7. [J] correctness-by-construction over cached state for a system this size. [U] U-8: the budget is a measurement still to be made.
- **Confidence.** Medium (High on "on read"; Medium on "the join is fast enough").
- **Would change my mind.** The benchmark (→ the fallback ladder, in order); a dashboard needing PRs for *all* exercises of a user on every page load → a maintained all-time table as a cache.
- **Round 1.** **Revised** together with D-06. Also corrected: the first fallback ("per-metric indexes") could not have worked with the query as written, because the branches read a materialised CTE — missed by three reviewers and the author, found by Astra.
- **Round 2.** **Revised**, in detail only; computing on read was kept by all three reviewers. A-6: the decision no longer claims "one pass" — that is one plan the planner may pick. B-1: the test this decision rests on is a fixed fixture and is never cut: the same sets through the SQL and through the domain `rank()` (`100 kg × 1` against `96 kg × 2`, equal scores on two dates, a kilogram set against a pound set, a zero-weight set), with the same entry and set for all three records. The `fast-check` version of it can be cut; the fixture cannot. B-13: the ladder gained its first rung; one reviewer wanted that index from the start, and it stays a fallback until a measurement asks for it. C-4 (the candidate's call): a name that matches no whole exercise name gets a fixed message that says the filter matches the whole name and points to `?exercise=` on history.
- **Round 3.** Kept. 3A-12: design §7 says in one sentence that on a tie within one day a date-only entry wins over a timed one, because its ordering value is earlier; a lifter logging twice in one day with one entry untimed is rare, and either answer names a real workout of that day. Putting `time_known` into the tie-break was not followed. 3B-8: the empty-result message quotes the normalised key it looked for.
- **After round 3 — the owner's time model.** **Revised**, in the tie-break only. With no local date (D-09) the first tie key is the instant; the 3A-12 sentence about a date-only entry winning within a day is gone, because a date alone is no longer accepted. Date predicates are half-open instants.

## D-12 — Epley at one rep: the brief's formula, for every rep count

- **Question.** The brief prescribes `weight × (1 + reps/30)`. What about `reps = 1`, zero weight, high reps?
- **Options.** (a) apply the formula literally for all reps (100 kg × 1 → 103.33); (b) `reps = 1` → the weight; formula for `reps ≥ 2`; (c) also cap or reject high reps.
- **The proposal, rejected.** (b): a one-rep set returns its own weight, as a documented deviation.
- **Decision.** (a). Reps are capped at 1 000 by validation (D-18) as a typo guard; weight 0 gives 0.
- **Why the proposal lost.** The argument for (b) was sound in the gym — a single at 100 kg *is* a one-rep max of 100, and the formula's own source says it "assum[es] r > 1" — but the brief is the specification being graded, and anyone checking a one-rep set with the brief open computes 103.33. The author also defended (b) as a display nuance; it is not. `100 kg × 1` against `96 kg × 2` is 103.33 against 102.40 under the brief's formula and 100 against 102.40 under the exception: the rule decides which workout holds the record.
- **What is kept of the domain point.** The README says that Epley overestimates a true single by 3.3 %, cites the "r > 1" source, and notes that the exception is a small change — one line in the domain function and the matching expression in the PR query — because nothing derived is stored (D-06).
- **Basis.** [V] V-6. [K] K-13. [J] a deviation from the grading specification must earn more than it risks; this one does not.
- **Confidence.** High.
- **Would change my mind.** Everfit saying the product treats a single as its own 1RM.
- **Round 1.** **Rejected.** Change → literal from Grok, Gemini, Opus and Astra; Astra's two-set example settled that it is not cosmetic. The realism audit found a real reader on each side (a grader, a lifter), so the choice went back to the candidate, who chose the brief's formula.
- **Round 2.** Kept by all three reviewers; the rejection of the first proposal stands. A-11: the number is called an estimate wherever it appears — `estimatedOneRepMax` in responses, "estimated 1RM" in the README and the OpenAPI text.

## D-13 — PR comparison takes two explicit ranges of instants

- **Question.** How is "this month vs last month" expressed (F3.5)?
- **Options.** `period=month` presets computed by the server; two explicit ranges from the caller; both.
- **Decision.** A `/personal-records/compare` endpoint requiring `from`, `to`, `compareFrom`, `compareTo` (instants; each range half-open, `[from, to)`), returning both PR sets and a delta inside `data`. Each pair is validated like any other range. Both periods are read in one `REPEATABLE READ` read-only transaction, so they describe the same moment. The delta is current minus previous: the absolute figure in the requested unit, the percentage without a unit. A period with no entries is a 200 whose `message` names the empty period or periods; its deltas are `null`.
- **Why.** "This month" depends on the viewer's zone and current date, which the server does not know (no user profile, no auth). Presets would need a `tz` or `asOf` parameter and bring timezone logic back into reads, undoing D-09. Explicit ranges are fully general (week vs week, quarter vs quarter) and trivial for any client to compute. Reusing the single-range query twice keeps one code path.
- **Basis.** [J]. Consistent with D-09.
- **Confidence.** Medium.
- **Would change my mind.** Reviewers reading "this month vs last month" as a literal preset requirement → add `period=month&asOf=<instant>&timeZone=<zone>` as sugar that expands to the two ranges — the one place a zone on reads could earn its keep.
- **Round 1.** **Accepted.** Conceded as right by the reviewers. Wrapping the two reads in one snapshot transaction (Opus) was withdrawn: a write landing in the milliseconds between them stores nothing wrong and a refresh shows the settled answer.
- **Round 2.** **Revised.** C-3 (the candidate's call) reverses the round-1 withdrawal: the two reads now share one snapshot. The round-1 reasoning still holds — a write landing between the reads stores nothing wrong — so this is cheap insurance and a one-sentence interview answer, not a fix for a realistic race: three lines of code. The two-connection test that would force the interleaving is not written; it would test PostgreSQL, not this code, and costs more than the feature. A-3: the response sits inside `data` like every other; `message` names the empty period or periods; the absolute delta is in the requested unit and the percentage has none.
- **Round 3.** Kept. 3B-8: the empty-period message carries the same whole-name hint as the PR endpoint and quotes the key. 3B-11: the README says a delta is computed from exact values, so it can differ by 0.01 from the difference of the two displayed figures (`104.37 − 103.33` shows as `1.03`, not `1.04`).
- **After round 3 — the owner's time model.** **Revised**, in the bounds. The four bounds are instants and each range is half-open, so last month's `to` is this month's `from` and no moment is counted twice or missed; `from >= to` is a 400. The caller computes the periods in its viewer's zone (D-09).
- **Round 4.** **Revised**, in detail. Bounds are rounded up to the millisecond before `from >= to` is checked; the empty-period message says "(included)" and "(excluded)" instead of "up to"; overlapping periods are accepted and each is answered on its own; each record carries `utcOffset`.

## D-14 — Bulk is a separate endpoint and atomic; ids assigned in input order

- **Question.** How is "multiple exercises in a single request" exposed, and what happens on partial failure (F1.3)?
- **Options.** One endpoint that always takes an array; single + `/bulk`; atomic vs per-item results (HTTP 207 style).
- **Decision.** `POST …/workout-entries` creates one (201 + `Location`); `POST …/workout-entries/bulk` takes `{ entries: [1..100] }`, validates everything first and stores all or nothing. The service generates one UUIDv7 per entry **in input order** (D-20), then sends two plain multi-row `INSERT`s in one transaction; sets are attached by the ids the application already holds. The response lists the entries in the order sent. History is a different order — newest first — so entries with the same instant (a session stamped with its start time, or back-filled entries given the same time) come back newest id first: for one bulk request, the reverse of the order sent. `/bulk` returns no `Location`, because it creates many resources. Invalid item → nothing stored, every error reported with its index path.
- **Why.** A single-resource POST with `Location` is the plainest REST contract; a distinct bulk route keeps each contract simple, and both share one DTO and one service method. Atomic is what a client logging "today's session" wants: one outcome, no reconciliation of partial results. Per-item results are valuable for imports of thousands of independent rows — not this use case. Assigning ids in the application removes a dependency on the order in which PostgreSQL returns rows from a multi-row insert, which the manual does not promise.
- **Basis.** [BP] atomic batch for small, user-initiated batches; partial success for large imports. [V] V-10. [J].
- **Confidence.** Medium.
- **Would change my mind.** A stated need to import historical data in bulk with tolerant failure handling.
- **Round 1.** **Revised** (the id rule; Opus found the undocumented row-order dependency). Keep on the two endpoints from Gemini, Opus and Astra; Grok's merge into one endpoint was not followed. Withdrawn: switching to `unnest` to stay under the protocol's bind-parameter limit — at the caps a request is at most 5 000 set rows × 6 columns = 30 000 parameters against a limit of 65 535 (K-16), and the caps are constants.
- **Round 2.** **Revised**, in detail only; the two endpoints and the atomic bulk were kept by all three reviewers. A-1: the revision had promised one order for both the bulk response and history, which the sort key contradicts; the two orders are now stated separately and each has a test. A-12: why `/bulk` has no `Location`, and what the single POST returns if `GET …/{id}` is cut (201 with the entry in the body and no `Location`). B-6: an array sent to the single endpoint, or a bare array sent to `/bulk`, is a 400 that shows the expected shape; a non-JSON body is a 415. B-7: every problem of a request comes back in one `errors[]`, held by a bulk test with two faults in different items.
- **Round 3.** Kept. 3B-9: one `errors[]` is stated as the result — field rules and cross-field rules (a body `userId` that differs from the path among them) are collected together — and the bulk test gains a third fault, a differing body `userId`. 3A-13: the ordering test's two date-only entries share a date.

## D-15 — Append-only writes, no content dedupe; no `Idempotency-Key` in the plan

- **Question.** What does handling "same user logging same exercise at the same time" mean (E5)?
- **Options.**
  1. Unique constraint on `(user, exercise, time)` → 409.
  2. Silent dedupe by content hash (previous plan).
  3. Client-supplied `Idempotency-Key`, replay on match.
  4. Nothing special.
- **Decision.** The answer to E5 is the shape of the write path: inserts only, PRs computed on read, bulk in one transaction — nothing two concurrent writers can corrupt, lose or tear. Two identical simultaneous requests create two entries, and the README says so under its own heading. Option 3 is **not in the plan**. The README names it as the next step and describes its shape: a claim row per `(user_id, key)` holding a hash of the request and the ids of the entries it created; a retry with the same key and body gets those entries back in the order first sent; the same key with a different body is refused; a request that finds its key still being processed waits a short `lock_timeout`, rolls back and answers "busy, retry". The README also says what a duplicate costs — one extra row in history and no change to any PR — and that deleting an entry is the first endpoint a second version would add.
- **Why.** In real use the E5 case is a double-tap, two devices syncing one session, or a coach and a client both entering a workout. The first two are duplicates only the client can identify — which is what a key encodes — and the third is two people who both meant it. Option 1 rejects legitimate data (two sessions of one exercise on a date-only day). Option 2 guesses intent and silently drops a genuine repeat: pull-ups before and after the main lift are two real entries. The brief asks about concurrent writes, not about client retries, and gives the client no header — so the key is a production-readiness extra, not the requirement.
- **Basis.** [V] V-5 (draft status — used as a convention). [BP] K-4. [K] K-10 (behind the README's description of the key).
- **Confidence.** Medium (High on "no content dedupe"; Medium on how much a reviewer expects the key).
- **Would change my mind.** A reading of E5 as "two identical concurrent requests must produce one entry even with no client support" → an opt-out content-hash guard limited to a short time window, with the trade-off documented.
- **Round 1.** **Revised**, in scope and in mechanism. Grok: cut the key from the first build — the brief's case has no client header. Opus: keep it, and say what a request does while the first is in flight. Astra: the flow as written never said what the losing writer reads. Gemini: a burst of same-key requests could hold connections. Result: optional slice (the candidate's choice), wait-then-replay with a second lookup, `lock_timeout` as the guard. Content-hash dedupe was proposed again (GPT-OSS) and rejected again. Withdrawn: a retry arriving after its key was purged, and the 20-requests-one-key test — no client does either.

## D-16 — Partial name match by `LIKE` over a per-user covering index; no trigram index

- **Question.** How is "exercise name (partial match)" made fast at 50k entries per user?
- **Options.** (a) `pg_trgm` GIN index on the name; (b) composite `btree_gin` (user + trigram); (c) resolve the term to the user's matching exercise keys first, then `= ANY`; (d) filter while walking the user's ordered history index, with `exercise_key` as an `INCLUDE` column.
- **Decision.** (d). `exercise_key` is already lowercase, so the predicate is `LIKE '%term%'` with wildcards escaped. The query is two-step — an index-only id page, then the full rows by primary key — because PostgreSQL filters on an `INCLUDE` column without heap access only in an index-only scan (design §9.2). **Fallback if the benchmark disagrees: (c), with no new table** — a loose scan of `ix_entries_exercise` lists the user's distinct exercise keys (about 150 probes), the term or the muscle group is matched against them in memory, and the newest `limit + 1` entries of each matching key are fetched with a `LATERAL` lookup on the same index and merged.
- **Why.** Every history query is already confined to one user and must return rows in date order. A global trigram index answers "which rows *in the whole table* match the term" — for a popular word that is millions of rows across users, which then still need filtering by user and sorting. Walking the user's own ordered index and filtering from the included column is bounded by that user's row count, needs no heap access, needs no sort, and stops at `limit` when matches are common. It costs zero extra indexes on the write path. Two cases walk the whole of the user's index: a term that matches nothing — which search-as-you-type produces constantly — and a term or muscle group that matches only a rarely logged exercise, where the page never fills. Both are in the benchmark, and fallback (c) answers both from the user's key list. Cost ceiling: the `LIKE` scan reads at most the user's rows inside the requested date range — 50 000 for the heavy user with no range, far fewer with `from`/`to` — and that ceiling is unmeasured (U-3); the no-match and rarely-logged cases are the ones that reach it, so they are the cases to measure.
- **Basis.** [V] V-4 (what pg_trgm does and its limits). [K] K-6. [U] U-3 — **a hypothesis until the benchmark confirms it**.
- **Confidence.** Medium.
- **Would change my mind.** Benchmark over 100 ms p95 for the no-match case or the rarely-logged-exercise case; or a requirement for fuzzy/typo-tolerant search (then trigram similarity is the right tool).
- **Round 1.** **Accepted**, with the fallback corrected. The first fallback list put per-metric PR indexes first, which do nothing for a slow name filter (Grok). Gemini's "resolve keys first" is fallback (c). A trigram index is no longer on the list: once the term is resolved against one user's few hundred exercise names there is nothing left for it to speed up. Gemini rated the scan a blocker; unmeasured either way, it stays a benchmark gate.
- **Round 2.** **Accepted**, with the fallback rewritten (B-11). Two reviewers showed independently that the `user_exercises` table of round 1 helped only the no-match case; the slow case is a term or a muscle group that matches a rarely logged exercise. The rewritten fallback covers both and needs no table, no change to the write path and nothing to keep in step. A-9: `ix_entries_exercise` is no longer described as "for PRs only". B-12: the rarely logged exercise is a benchmark case with its own budget (under 100 ms).

## D-17 — Nested REST resource, `/v1`, `userId` in the path; body `userId` accepted when equal

- **Question.** URL shape, where `userId` goes (T4), versioning, response envelope.
- **Options.** `/users/{userId}/workout-entries` vs `/workout-entries?userId=` vs `userId` in the body.
- **Decision.** Nested under `/v1/users/{userId}/…`; `userId` is an opaque string (1–64 chars, `[A-Za-z0-9_.-]`) stored as text; URI versioning; success envelope `{ data, page?, message? }`; unknown users are not an error (no user store). The path is authoritative. A `userId` in the body — on a single entry or on any bulk item — is accepted when it equals the path value and is not stored twice; a different value is a 400 naming the field.

The service does not own user identity, so it must not assume an id format. An envelope leaves room for `page` and the "appropriate message" the brief requires for empty results. The brief lists `userId` among an entry's fields, so the first request a reviewer writes from the brief has it in the body; answering that with a 400 punishes reading the brief. A mismatch must still fail loudly — silently preferring one of two different ids would store data under the wrong user.
- **Basis.** [BP] REST resource nesting for strict ownership; URI versioning is Nest's built-in default style. [J].
- **Confidence.** High.
- **Would change my mind.** Nothing likely.
- **Round 1.** **Revised.** The only unanimous change: every reviewer, and the first decision log's own "would change my mind". Astra added the bulk items.
- **Round 2.** Kept. One reviewer's "Modify" was a list of what still fails a first request written from the brief, none of it about `userId`: a non-JSON body and an array where an object is expected (B-6, recorded under D-18 and D-19).

## D-18 — Validation rules; limits are constants

## D-19 — RFC 9457 problem details for errors

- **Options.** Nest's default `{ statusCode, message, error }`; a custom envelope; RFC 9457.
- **Decision.** `application/problem+json` with extensions `code` (stable machine code), `errors[]` (`{ path, message }`) and `requestId`, produced by one global exception filter. Validation failures are 400. A body sent with any content type other than `application/json` is 415. 409 is used by the three catalog conflicts (D-27) and nowhere else; 401 exists only once the admin guard is switched on; 422 is not used.

One filter guarantees every failure path — validation, 404, malformed JSON, database down, unexpected — has the same shape and never leaks internals. 400 for validation matches Nest's default and common practice. Messages say how to fix the request, not only what is wrong (the offset-less date-time message is the model).
- **Basis.** [K] K-2. [J] 400 vs 422 for validation is a long-running style debate; consistency matters more than the pick.
- **Confidence.** High.
- **Round 1.** **Accepted.** Not contested.
- **Round 2.** **Accepted.** A-4: the offset-less date-time message says the *instant* is unknown — the day is in the text — and still names the three fixes. B-6: the 415 exists because `curl -d` with no content-type header is the most likely first mistake of someone trying the API by hand. B-7: every problem of a request in one `errors[]`.
- **After round 2.** The catalog adds three 409 codes (`EXERCISE_EXISTS`, `MUSCLE_GROUP_EXISTS`, `MUSCLE_GROUP_IN_USE`) and, once the guard is on, a 401 (`UNAUTHORIZED`).
- **Round 3.** Kept. 3B-1 and 3A-10: a foreign-key violation (`23503`) is mapped — a 400 listing the known groups on an exercise write, 409 `MUSCLE_GROUP_IN_USE` on a group delete; `ON DELETE RESTRICT` does not produce a 409 by itself. 3A-6: the 415 ignores media-type parameters such as `charset`. 3B-6: the 401 carries `WWW-Authenticate: Bearer`. 3B-9: one `errors[]` per request, stated as the result of how the rules run.

## D-20 — UUIDv7 primary keys, generated in the application

- **Options.** `bigserial`; UUIDv4; UUIDv7 from PostgreSQL's `uuidv7()`; UUIDv7 from the application; ULID.
- **Decision.** The service generates entry ids with the `uuid` package's `v7()`, in input order, before inserting. The column keeps `DEFAULT uuidv7()` for the benchmark-data seed and manual inserts.
- **Why.** UUIDv7 is safe to expose (no enumeration, no row-count leak), needs no coordination, and is time-ordered — inserts append to the right edge of the index instead of scattering like v4, and the id is the final tie-breaker of the pagination order. Generating it in the application gives two things the database default cannot: the service knows every id before the insert, so sets are attached without relying on the order of returned rows (D-14); and ids made within one request increase in input order, which gives entries of one request that share an instant a defined order in history — newest id first, the reverse of the order sent (D-14). The `uuid` package keeps a per-process counter, so ids made in the same millisecond still increase (V-10). Across replicas the order is by millisecond only — irrelevant here, because order matters only inside one request.
- **Basis.** [V] V-4, V-10. [K] index locality of time-ordered keys.
- **Confidence.** High.
- **Would change my mind.** Nothing likely; dropping the `uuid` dependency would mean hand-rolling the same counter.
- **Round 1.** **Revised**, from "generated by PostgreSQL". Grok first questioned ordering inside one request; Opus identified the actual dependency (row order of a multi-row insert). The choice of the `uuid` package is the author's, made while applying the approved list.
- **Round 2.** The author's call (the `uuid` package) was reviewed and kept by all three reviewers. B-8: the package is ESM-only (verified), so the first slice imports `v7` in a Jest test before anything depends on it. A-1: increasing ids do not make a history page read in input order — descending ids list one request's date-only entries in reverse. The sentence that said otherwise is corrected here and in D-14.

## D-24 — Output rounding and original-unit echo

- **Decision.** Responses express weights in the requested `unit` (default `kg`), rounded half-up to 2 decimals, as JSON numbers. If the requested unit equals a set's original unit, the stored original is returned unchanged. Every set includes `original: { weight, unit }` — the number as it was sent and the canonical unit code (`lbs` comes back as `lb`). Derived values (volume, estimated 1RM, deltas) are computed from the exact kilogram values, converted, and then rounded once. In OpenAPI, `unit` is an enum on output and a string with the accepted spellings on input.
- **Why.** Two decimals is finer than any plate increment and avoids noise like `102.05828325`. Returning the original untouched prevents `225 lb` coming back as `224.99`/`225.01`. Echoing the original lets a client show what the athlete actually typed regardless of the display unit.
- **The round-1 limit is gone.** With four-decimal kilograms, a pound set's *volume* shown back in pounds could be 0.01 lb off between 31 and 50 reps. With exact kilograms (D-08) it cannot: `6 lb × 50` shows 300 lb.
- **Basis.** [J]. [BP] round only at the presentation boundary.
- **Confidence.** Medium.
- **Would change my mind.** A preference for strings to carry decimals exactly in JSON (defensible; numbers chosen for client ergonomics).
- **Round 1.** **Accepted.** Keep from Grok, Gemini and GPT-OSS; the modification Opus and Astra asked for was withdrawn with D-08's.
- **Round 2.** **Revised.** A-7: "verbatim" was wrong for the unit — the spelling sent is not kept; the original is the number as sent and the canonical unit code. ## D-27 — Catalog administration: open admin endpoints behind a two-line guard

- **Question.** Who changes the catalog, through what, and what does a change do to the thousands of logged entries that carry an exercise's key?
- **Status.** New after round 2; **reviewed in round 3**, where all three reviewers kept it with modification (round-3 summary, sections 3 and 9). Each point says who decided it: the owner (asked once, in one batch, before any document was edited; the recommended option was taken on all six questions) or the author (points settled while applying, listed so the owner can redirect any of them).
- **Decision.**
  - *Endpoints — the owner.* Public reads: `GET /v1/exercises`, `GET /v1/exercises/{exerciseKey}`, `GET /v1/muscle-groups`. Writes, all under `/v1/admin`: `POST /admin/exercises` (201 + `Location`; 400; 409 `EXERCISE_EXISTS`), `PUT /admin/exercises/{exerciseKey}` (200; 400; 404), `DELETE /admin/exercises/{exerciseKey}` (204; 404), `POST /admin/muscle-groups` (201; 400; 409 `MUSCLE_GROUP_EXISTS`), `DELETE /admin/muscle-groups/{name}` (204; 404; 409 `MUSCLE_GROUP_IN_USE`). Options: write verbs on `/v1/exercises` itself; a separate `/v1/admin` prefix. The prefix won because one controller then holds exactly the routes a guard has to cover, and a gateway rule can cover them with one path pattern.
  - *Authorization — the owner: off in v1, easy to switch on, stated openly. The author: the guard's shape.* The five write routes are open. `AdminTokenGuard` is written and tested and is left off by two commented-out lines on `CatalogAdminController`: the import of `AdminOnly` (a decorator exported from the guard's file, `AdminOnly = () => UseGuards(AdminTokenGuard)`) and `// @AdminOnly()` on the class — two lines, because an unused import fails the lint. Switched on, it compares SHA-256 digests of `Authorization: Bearer <token>` and `ADMIN_API_TOKEN` with `timingSafeEqual`, so a token of any length is compared without throwing; it answers 401 `UNAUTHORIZED` with `WWW-Authenticate: Bearer`, and fails closed: with the variable unset it refuses every request. A unit test covers a missing header, a wrong scheme, a wrong token, a token of a different length and the unset variable; a second test applies the guard to the real controller and checks every write route answers 401. Options: a TODO and no guard code; a setting that switches a guard on at run time; a tested guard left off by two lines. The last was chosen: the owner named it as acceptable, the open state is visible in the code and in a diff, and there is no setting that can sit in the wrong position unnoticed. A static token is a placeholder — the platform's real answer is a role check on the caller's identity, and the guard is where it would go.
  - *Muscle groups — the owner.* A closed list held in data: a `muscle_groups` table, enforced by a foreign key. An unknown group on an exercise write is a 400 that lists the known ones; a new group is one admin call and no deploy. Options: free text on each exercise; a list in code or configuration; a table. With writes open to anyone, free text lets a typo become a group that no filter will ever be asked for, and a list in code brings the deploy back. The author added: no rename for a group in v1 (add the new one, PUT the exercises, delete the old one).
  - *Rename — the owner.* The key is fixed. PUT may change the muscle groups and any spelling that keeps the same key (`bench press` → `Bench Press`); a `name` with a different key is a 400 saying a different name is a different exercise — POST it, and delete the old one if it is no longer wanted. Options: a rename that rewrites every logged entry (it merges the records of two names); a rename that leaves the entries behind (they lose their muscle groups); aliases (product rules, D-07); a fixed key.
  - *Delete — the owner.* It removes the catalog row and nothing else, and it is a hard delete. Logged entries are never touched: they stay in history with their PRs intact, show `muscleGroups: []`, and stop matching the muscle-group filter. POSTing the same name again restores the mapping for all of that history, because groups are resolved by key at read time. Options: refuse while entries exist (an exercise could then never be removed); cascade to the entries (destroys a user's history from an open endpoint); soft delete (keeps nothing a POST does not bring back); the row only.
  - *Seed — the owner.* Each item of `seed/exercise-catalog.seed.json` is given to a database once. A ledger (`catalog_seed_ledger`) records which items this database has received; a redeploy adds only items new to the file; an edited row stays edited; a deleted row stays deleted. It runs in the one-shot `migrate` step, after the migrations. Options: seed only an empty catalog (a later file's new exercises never arrive); upsert from the file at every deploy (overwrites an admin's edit); insert whatever is missing at every deploy (brings deleted rows back); the ledger. The author added: the file is validated before any write and an invalid file fails `migrate`; the whole `migrate` entry runs under one session advisory lock, taken before the ledger is read; an exercise is inserted with `INSERT … ON CONFLICT DO NOTHING RETURNING`, and its links are written only when that insert returned a row, so an admin's own row that a later file also adds stays as written, groups included; the ledger insert is `ON CONFLICT DO NOTHING`; an item removed from the file or changed in it does nothing; a new file item naming a group that is not in the database (an admin deleted it) is inserted without that group, with a warning naming both. Round 3 reviewed these and changed the order (lock first) and the link rule (3B-2).
  - *Scope and time — the owner.* The catalog is core work: the tables, the seed and exercise create, update and delete are never cut; only the two muscle-group write routes are on the cut list; the admin API is built after PRs and before the final write-up; the stated figure was 20–22 h, restated at 23–25 h after round 3 (D-26).

## D-28 — Libraries before hand-written code

- **Question.** When the code needs a general-purpose function (a type check, a safe read of a field, query validation, percentiles), is it written by hand or taken from a library?
- **Status.** New: the owner's convention, set after the review of the implementation plan. Not reviewed by a debate round.
- **Decision.**
  - *The owner.* Stable, clean code and sound error handling decide. Before writing a function, use what exists: a Node built-in or a library already in the stack (Nest's pipes, class-validator, decimal.js, `Temporal`, `uuid`), or a well-kept dependency added for it. Where a built-in is easier to get wrong, use lodash instead; the owner's example is reading a property of a value that may be `null`, which `get` does without throwing.
  - *The author.* For a typed value, optional chaining (`a?.b`) is the built-in that does not throw on `null`, and the compiler checks its path, which a string path given to `get` loses; so `get` is used on values typed `unknown`, such as a caught error, and `isPlainObject` answers "is this a JSON object" (`typeof null` is `'object'`). Code is written by hand only for domain logic (keys, ranking, the seed plan, the catalog refresh rules), for a framework hook (the problem-details filter, the admin guard) or for a one- or two-line helper (escaping `LIKE` characters, formatting an offset), with the reason in a comment. CommonJS or dual packages are preferred, because an ESM-only one needs a Jest transform entry, as `uuid` does.
  - *The owner's one exception.* The benchmark keeps its own request loop and its p95 budgets. autocannon, the usual Node load tool, reports p90 and p97.5 but not p95 (V-23); the percentiles come from `simple-statistics`.
  - *In the plan.* Query parameters are class-validator DTOs, which reject unknown and repeated parameters; Nest's `ParseUUIDPipe` gives the 404 for a non-UUID id; Express's `req.is()` decides the 415; lodash `isPlainObject` checks body shapes and decoded cursors, and `get` reads driver error codes; the seed file's shape is a class-validator DTO; the clean-image check uses curl's own retry.
- **Why.** A library that many projects run has met edge cases a hand-written helper has not, and a reviewer recognises it at a glance. Checking the plan against the rule found one such case at once: Drizzle 0.44 and later wraps every driver error, so reading `err.code` directly would have turned the documented 409 (a muscle group in use) and 503 (database down) into 500s.
- **Basis.** The owner's convention. [V] V-23. [J] on where the hand-written exceptions lie.
- **Confidence.** High.
- **Would change my mind.** A dependency that turns out unmaintained or vulnerable; a library form that costs more code than the helper it replaces.
