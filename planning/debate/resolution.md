## 5. Withdrawn as unrealistic — not built

Each of these was accepted at some point in the round and then failed the
question *who sends this, how often, and what do they see?*

| Item | Why it was withdrawn |
|---|---|
| Store kg to eleven decimals | The example needed a load of `88.185 lb`, which is 40 kg written in pounds. Four decimals is 0.1 g |
| Guard against `timestamptz(3)` rounding across midnight | Needs sub-millisecond input in the last half-millisecond of a day; the stored date comes from the request text anyway |
| Snapshot transaction around the two compare reads | A write landing between two reads stores nothing wrong; a refresh shows the settled answer |
| `unnest` rewrite for the bind-parameter limit | The largest allowed request is about 30 000 parameters against a limit of 65 535, and the caps are constants |
| Startup check of limits against column widths | Existed only because the caps were configurable, which nobody asked for |
| Retry the claim if the key was purged in between | A key would have to expire in the instant its own retry arrives |
| Bind the cursor to its filters | Reuse under other filters is a client bug that gives an odd page, not wrong data |
| A test firing twenty identical requests at once | No client does that. Replaced by two at once plus one later |

**Changed later.** Round 2 brought two of these back (§14):

- *Exact kilograms.* The round-1 example needed a load nobody enters. Round
  2 brought one that ordinary pound plates produce: `100 lb × 10` and
  `200 lb × 5` are the same volume, and four decimals break the tie.
- *The snapshot around the two compare reads.* The round-1 reasoning still
  holds — nothing wrong is stored. It came back as three lines of cheap
  insurance and a one-sentence interview answer, not because the race is
  realistic.

Binding the cursor to its filters was proposed again and not followed again
(§15). The two idempotency-key rows concern a key that is no longer built.

## 7. Calls the author made while applying the list

Nobody has reviewed these. They follow from approved items but are not in
the approved list word for word.

1. **`time_known` flag instead of a nullable column.** The list says
   `performedAt: null` for date-only entries. A null in storage would break
   keyset paging, which compares `(performed_on, performed_at, id)`. So
   `performed_at` stays non-null as an ordering key, a boolean records
   whether the time is real, and the API returns `null`. Opus and Astra had
   each proposed this shape.
2. **The `uuid` package's `v7()` for application-generated ids.** Its source
   keeps a per-process counter, so ids made in the same millisecond stay in
   order (research note V-10). One small dependency.
3. **`Temporal` for the zone conversion.** Built into Node 26, typings in
   TypeScript 6.0 (V-8); no dependency added.
4. **The alias list**: `lbs` for `lb`, `kgs` for `kg`. Anything else is one
   more string in the same list.

**Reviewed in round 2.** All four were kept. Two gained a detail: the
ordering value of a date-only entry moved 14 hours earlier (call 1, B-4),
and the first slice imports `v7` under Jest because the package is ESM-only
(call 2, B-8).

## 17. The owner's catalog requirement

**What was asked.** D-07 kept the catalog in a JSON file read at boot and
named its own trigger for change: "a need to edit the mapping without a
deploy". The owner reported exactly that — exercises are updated often, and
a developer cannot be needed each time. Fixed points of the requirement:
the catalog in a database table behind the existing `ExerciseCatalog` port;
admin endpoints to add, update and remove exercises; a migration and a
seed-from-JSON step so that a fresh `docker compose up` gives a working
catalog; authorization off for now, with a guard that is easy to enable and
documents that say openly that the write endpoints are unauthenticated; no
code change to add or change an exercise.

**What it overturned.** Every reviewer in both rounds had ruled for the
file — in round 1 four of them asked for the first design's catalog tables
to be removed. Their argument was that tables served an admin workflow
nobody had asked for. The owner has now asked for it. The argument was sound
on what was known; what was missing was the question to the owner of how
often exercises change. What still holds from D-07: unknown exercises stay
loggable, entries carry no reference to the catalog, muscle groups are
resolved by key at read time, and there are no aliases.

**The owner's six decisions**, taken in one batch before any document was
edited. Each was the recommended option.

| # | Question | Chosen | Not chosen |
|---|---|---|---|
| 1 | Rename | The key is fixed. PUT may change the muscle groups and any spelling that keeps the same key; a different name is a new exercise | A rename that rewrites logged entries; a rename that leaves them behind; aliases |
| 2 | Delete | The catalog row only. Logged entries are never touched: they stay in history with their PRs, show no muscle groups, and stop matching the muscle-group filter. Re-adding the name restores the mapping | Refuse while entries exist; soft delete; delete the entries too |
| 3 | Muscle groups | A closed list held as data, enforced by a foreign key. An unknown group is a 400 listing the known ones; a new group is one admin call | An open vocabulary, where a typo becomes a group; a list fixed in code |
| 4 | Seed | Each item of the file is given to a database once, recorded in a ledger. A redeploy adds only what is new in the file; edits stay; deletions stay | Insert only when the tables are empty; upsert on every deploy, which overwrites an admin's edit |
| 5 | Routes | `GET /v1/exercises`, `GET /v1/exercises/{exerciseKey}`, `GET /v1/muscle-groups`; `POST`, `PUT`, `DELETE` under `/v1/admin/exercises`; `POST` and `DELETE` under `/v1/admin/muscle-groups` | Write routes on the public paths, with nothing in the URL to hang a guard or a gateway rule on |
| 6 | Scope and estimate | Core, about 2.75 h more, stated as 20–22 h. The tables, the seed and exercise create / update / delete are never cut; only the two muscle-group write routes join the cut list. The admin routes are built after PRs | The admin routes as an optional slice; a smaller figure paid for from the buffer |

**Calls the author made while applying it.** Ten, as in design §17. Round 3
reviewed all ten: eight were kept and two were fixed — call 2 (the boot
rule) and call 4 (the guard). Section 20 says how; the text below is the
calls as first made.

1. **Reads go through an in-memory snapshot per process**, reloaded every
   30 seconds (`CATALOG_REFRESH_SECONDS`) and at once on the replica that
   handled a write. The port stays synchronous and the history query keeps
   the shape the benchmark measures. Not chosen: a read per request,
   `LISTEN` / `NOTIFY`, a version counter.
2. **Failure behaviour.** No catalog at boot: retry for about ten seconds,
   then exit non-zero. A failed refresh: keep the last good snapshot and log
   a warning. A stale catalog does not fail readiness.
3. **One function makes every key** — on logging, on every catalog write, on
   the route's path value and in the seed — with no database `CHECK`
   repeating the rule. One integration test holds it.
4. **The guard's shape.** `AdminTokenGuard` is written and tested, compares a
   bearer token with `ADMIN_API_TOKEN` in constant time, fails closed, and is
   one commented-out line on the one controller that holds the five write
   routes (two lines after round 3: the import and the decorator). Not chosen: a to-do with no guard code; a runtime switch that
   could be left off by a missing variable.
5. **Seed details.** It runs inside the one-shot `migrate` step, after the
   migrations, in one transaction under an advisory lock. An invalid file
   fails the step. An admin's own row wins over a later file item with the
   same key. An item removed from the file, or changed in it, does nothing.
6. **PUT is a full replacement, last write wins**, with no `ETag`. A muscle
   group cannot be renamed: add the new one, move the exercises, delete the
   old one.
7. **The catalog's own GET routes read the tables**, not the snapshot; the
   exercise list is not paginated.
8. **Field rules**: an exercise name of 1–100 characters; 1–10 muscle
   groups, no repeats, order kept; a group name of 1–40 characters.
9. **Where the documents say the routes are open** — five places: a warning
   block near the top of the README; its "Catalog administration" section;
   the OpenAPI tag and each operation's description; a comment in
   `requests.http`; design §2 and the note under its route table.
10. **The compose profile for benchmark data is renamed `seed` → `bench`**,
    so that "seed" means the catalog everywhere.

**What an anonymous caller can do** through the open routes: change which
muscle groups entries show, and what the muscle-group filter matches, for
every user. **What they cannot do through these routes:** read, change or
delete a logged entry or a PR. (Round 3 added the qualifier: the rest of
the API has no authentication either, T4.)

Design: §5 (tables), §10 (everything else). Decisions: D-07 and D-27.

## 21. After round 3 — the owner's time-model change

**The case.** An athlete trains at `2025-02-10T05:30:00+07:00` in Vietnam
and at `2025-02-10T20:30:00-07:00` in the US. The two workouts are 29 hours
apart, yet the model of rounds 1–3 stored the same local date for both, so a
date range could not separate them and no viewer's timeline matched the
stored days. No reviewer of rounds 1–3 raised it. The owner also noted that
the brief's `date` is a field name and mandates no type.

**The direction the owner and the author agreed:** store the UTC instant
only; `date` is a date-time with `Z` or an offset; reads take half-open
instant ranges and no zone; order, cursor and indexes on
`(performed_at, id)`; no user-settings table.

**A review of that direction against real use** (the author model, at the
owner's request, with the facts run on Node 26 — research notes V-17)
found two serious gaps and several details:

| # | Finding | Outcome | Decided by |
|---|---|---|---|
| 1 | A coach in another zone, or an athlete who has moved, sees a workout on another day (a Monday 06:00 session in Hanoi is Sunday 15:00 in Los Angeles) | Accepted as the intended product. Storing the original offset for display was offered and **not chosen**; the README names it as the next step. *Round 4: stored for display (§22)* | Owner |
| 2 | A date-only `date` would be a 400 on a reviewer's most natural first request, and importers that invent midnight UTC move entries to the previous day for every viewer in the Americas | First applied as: a date alone is stored as 12:00 UTC with `time_known = false`. **Then reversed:** `date` has one format, a date-time with `Z` or an offset; a date alone is a 400 whose message shows a full date-time, and the README tells a client that knows only the day to choose noon in the athlete's own offset — the client knows that zone, the server does not | Owner |
| 3 | No bound on the future or the past | No later than now + 15 minutes (catches a local time sent with `Z` east of UTC); nothing before 1900-01-01 | Owner |
| 4 | Two time fields in responses would now hold one value | `date` is the stored instant; `performedAt` is gone (a `timeKnown` field went with the date-alone rule) | Owner |
| 5 | A `+` in a query string arrives as a space | A space in exactly the offset's place is read as `+`. *Round 4: widened to every accepted offset form (§22)* | Author |
| 6 | `Temporal` silently ignores a zone in brackets, even a contradicting one | A zone in brackets is a 400. *Round 4: accepted and ignored (§22)* | Author |
| 7 | A half-open range with equal ends is empty | `from >= to` is a 400 | Author |
| 8 | Callers that add a fixed number of hours misplace workouts across daylight saving | The README gives the `Temporal` recipe, and an integration test computes Los Angeles weeks across 2025-03-09. *Round 4: replaced by a boundary test (§22)* | Author |
| 9 | A date alone at noon UTC can be 26 hours ahead of now at UTC+14 | Bounded as a date while the rule stood; moot once a date alone was refused | Author |

**Gone from the design:** `performed_on`, `time_known`, the `timeZone` field, the rule for
wall times in a daylight-saving gap or overlap, the made-up ordering value
for date-only entries and the `Z` caveat. The non-UTC test zones stay; they
now guard the instant path.

**Applied** to design §3, §5, §7, §8 (rewritten), §9.1–§9.4, §9.6, §11, §12,
§14, §15, §16 and §17; decision log D-09 (rewritten), D-10, D-11, D-13,
D-18, D-19, D-22 and D-26; requirements A1 and A6; research notes V-9, V-13,
V-17, K-18, U-7 and U-22 to U-24.

**The estimate stands at 23–25 h.** The zone conversion and its tests leave
slices 4–5; the bounds, the `+` rule and the daylight-saving test arrive.
The author judged the two about even.
